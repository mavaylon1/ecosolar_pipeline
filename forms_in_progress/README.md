# forms_in_progress

Proving ground for city permit forms before they're promoted to the production pipeline
(`forms/<city>/` + `forms/registry.py`, wired into `pipeline/runner.py`). Nothing in this
directory is live — it exists to test whether a city's field mapping actually works against
real JobNimbus data before committing to it.

## How it fits together

```
registry.py       Single source of truth: which cities, which forms, which template/mapping
                   files. Add a new city or form here — nothing else needs to change.
example_jobs.py    Pulls a real example job from JNB for a city (find_example_job), and
                   builds the extended permit-data schema these draft forms need
                   (build_example_data / extend_permit_data).
build_data.py      Driver: for every city in registry.py, pulls its example job and writes
                   <city>/permit_data.json. Also regenerates PROGRESS.md.
verify.py          Shared JNB-source-per-field table + the logic that turns a fill into a
                   human-readable VERIFY csv (PDF field -> JNB source -> value -> status).
run_all.py         Driver: for every (city, form) in registry.py, fills the PDF and writes
                   its VERIFY csv. All output goes to output/.
output/            Generated only — filled PDFs, VERIFY_<form>.csv, fill_reports.json.
                   Nothing depends on this directory being up to date; delete it and
                   re-run run_all.py any time.
<city>/            Per-city inputs: mapping_<form>.json (or mapping.json if there's only
                   one form) and permit_data.json (the example data pulled by build_data.py).
                   Anything genuinely one-off for that city's PDF (e.g.
                   westminster/fix_address_field.py, which works around a duplicate-field
                   bug in the city's own PDF) lives here too.
PROGRESS.md        Auto-generated by build_data.py — which JNB job was pulled per city.
RUN_NOTES.md       Historical findings log from the first pass through all 6 forms
                   (bugs found, open questions). Not regenerated — read for context.
```

## Running it

```bash
.venv/bin/python forms_in_progress/build_data.py   # pull/refresh example data per city
.venv/bin/python forms_in_progress/run_all.py       # fill every form, write output/
```

`build_data.py` is safe to skip if you just want to re-fill with the data you already have
(e.g. after editing a mapping.json) — only re-run it to pick up a different or more-complete
example job.

## Adding a new city or form

This is the part that matters for onboarding the rest of `pending_forms/` — Anaheim, Corona,
Fullerton, Irvine, Kern County, LA County, Long Beach, Orange, Pomona, Redlands, San Diego
County, Stanton, Yorba Linda are all sitting there as raw source PDFs, not yet wired in here.

1. If the source PDF is flat (no AcroForm fields), it needs converting first — see
   `pending_forms_fillable/` for that process; it's intentionally hand-done per form, not
   automated.
2. Write `mapping_<form>.json` (or `mapping.json` for a single-form city) under a new
   `forms_in_progress/<city>/` folder, using an existing one as a template. Reuse the
   existing schema keys (`project.*`, `property.*`, `owner.*`, `applicant.*`,
   `contractor.*`, `workers_comp.*`, `city_license.*`, `business.*`, `solar.*`,
   `solar_use.*`, `reroof.*`) wherever the new form asks for the same real-world fact —
   don't invent a new key name for something already covered.
3. If the form needs a genuinely new fact no existing schema key covers, add it once in
   `example_jobs.py`'s `extend_permit_data()` (or, if it's directly from the base JNB job/
   contact, it may already be available via `pipeline.transformer.build_permit_data()`) and
   once in `verify.py`'s `JNB_SOURCE` table — not per-city.
4. Add the city (and its form(s)) to `registry.py`. That's the only place `build_data.py`
   and `run_all.py` need to know about it.
5. Run `build_data.py` then `run_all.py` and check `output/<city>/` for the filled PDF and
   VERIFY csv.

Custom per-field logic (checkbox position quirks, a duplicate-field workaround, a form-
specific transform) belongs in that city's own mapping.json/script, not in the shared
modules — the shared modules (`registry.py`, `example_jobs.py`, `verify.py`, `run_all.py`)
should stay generic. If you find yourself adding an `if city == "..."` branch to any of
them, that's a sign the logic belongs in the city's own files instead.

## Promoting a form to production

Once a form's mapping is confirmed accurate (per `RUN_NOTES.md`'s open questions being
resolved, real static values filled in, and no unexplained "needs_review" issues), moving
it to production means: copying its template + mapping.json into `forms/<city>/`, and
registering it in `forms/registry.py` / `pipeline/runner.py`. That registry currently only
supports one form per jurisdiction — it'll need to support multiple (like Huntington Beach's
solar + asbestos) before any multi-form city here can go live. Not started yet.
